## Topic

新リポジトリ ptcg-agent-debate（Kaggle「Pokémon TCG AI Battle」コンペ、https://www.kaggle.com/competitions/pokemon-tcg-ai-battle）の初期開発方針を、以下の4点について1つの具体案に合意せよ。

1. **プレイアルゴリズム**: 初期実装のアーキテクチャと、その後の育成（強化）方向。
2. **デッキ選定戦略**: 最強デッキをどう発見・確定するか。
3. **日次改善ループ**: 計算資源は「ローカル1日8時間まで、CPU + RTX 3080 Ti、費用ゼロ」。この予算で日々強くする運用ループ（計測→改善→昇格判定）をどう設計するか。
4. **最初のマイルストーン3つ**（各≦数日規模）。

## 前提・制約（実測済みの事実 — 尊重すること）
- エンジンは cabt（Python）。乱数シード注入は不可（seedペア対戦は組めない）。提出は main.py 単体、ターン時間予算あり、fault（違法手/時間切れ）は即敗北級に重い。
- 評価は Wilson CI ベース。大 N の A/B は非現実的で、small-N screen → 上位のみ large-N confirm の2段方式が確立済み。昇格判定は集約 CI のみで行う。
- 兄弟リポジトリ（ローカルで読める: /workspaces/ptcg-agent-{matsu,take,ume,fable,core,zero}）の実績:
  - matsu = 決定化MCTS。提出版 0.709 (fault 0)。クロス対戦で 0.74〜0.87 とトップ。value net・ターンソルバー・Early Cutoff の追加実験はいずれも有意差なし（champion維持）。
  - take = ルールベース特化。0.44〜0.66。fallback穴の trace 集計で改善する手法が確立。
  - ume = 学習系（PPO/自己対戦/報酬shaping/リーグ）。0.10〜0.36 で最弱。学習系の昇格はほぼ全て失敗した歴史。
  - fable = 決定化MCTS + take式ルール統合 + 4層フォールバック。vs Random 0.98 / vs Greedy 0.64 / vs matsu 0.458（互角）。
  - デッキ選定 = 26候補 greedy screen→confirm で champion デッキ勝率 0.8165 CI[0.8025, 0.8297]（25,800戦 fault 0）。compare_decks.py はエージェント非依存。
- Python の agents 名前空間衝突があるため、対戦比較は subprocess 隔離が必須。

## 論点（ここで意見が割れるはず — 具体的に議論せよ）
- 既存最強（matsu ≒ fable）と互角止まりの現状を超えるには何を変えるべきか:
  (a) 探索のさらなる強化（determinization 数・rollout 品質・時間管理・実装高速化）、
  (b) RTX 3080 Ti を活かした AlphaZero 型 self-play 学習との融合（ume の失敗履歴をどう回避するか）、
  (c) 対戦相手モデリング / メタ読みデッキ最適化、
  (d) その他。
- 「1日8時間・長期育成」という予算は学習系に有利に働くか、それとも探索チューニングに回す方が期待値が高いか。
- 新リポジトリは何をベースに scaffold するか（fable ベース? core ベース? ゼロから?）。

(3) **日次改善ループ**: 1日8時間を、約1時間の回帰・fault/時間計測、約2時間の複数案 small-N screen、約4時間の上位1〜2案 large-N confirm、約1時間の trace 集計・結果記録・翌日仮説作成に割り当てる。乱数 seed 対応は前提にせず、独立試行を集約する。毎日、勝敗、Wilson CI、先後、matchup、fault、p50/p95思考時間、fallback 到達箇所を保存する。昇格判定は事前固定した対戦混合の集約 CI のみで行い、同点・CI重複・fault発生・時間超過なら champion 維持とする。GPU 学習は有望な教師データが蓄積した日に screen 枠内で実施し、探索改善との計算資源配分も同じ昇格基準で決める。

(4) **最初のマイルストーン3つ**: ① 1〜2日で fable ベースの最小 agent、単一ファイル提出ビルド、deadline/fallback、subprocess 対戦 harness、fault・時間・Wilson CI レポートを再現する。② 2〜3日で26デッキの screen→confirm パイプラインを動かし、固定相手混合に対する初代 champion デッキと再現可能な評価表を確定する。③ 2〜3日で MCTS trace と fallback 穴の分類を導入し、時間配分・枝刈り・rollout 改善案、および小型蒸留モデル案を同一 champion に対して比較し、集約 CI を通過した最初の改善だけを昇格する。
